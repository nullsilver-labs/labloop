# Pi workers, first probes, 2026-09-15

Can an open model, served locally by llama.cpp and driven by Pi (pi.dev), meet the
worker contract at all? The smallest campaign that can kill the idea is the M1 MNIST
probe (`../labloop-m1`, Sonnet, 2026-09-09), re-run on a local model with the same task,
data, labels, greedy selection, five-candidate cap and pre-fixed threshold. Two models,
one after the other on the same server (`scripts/llm-server.sh`, GPU 0, 32k context,
`--jinja`), with candidates trained on GPU 1. Branch `pi-workers`, tooling commit
`ebcb6fe` for gpt-oss and `7d14acd` for Qwen, the latter with result clipping. The
output-limit continuation came after both.

Read against M1's kill criteria only: a worker produces a runnable candidate inside 40
turns, and a candidate costs a small fraction of a session. Nothing here compares models
on quality. Five candidates on MNIST sit at the noise floor, as M1's caveats already
said.

## gpt-oss-20b (`../labloop-pi-probe-20260915`, campaign `pi-probe-gptoss`)

| | Pi + gpt-oss-20b (local) | M1: Claude Code + Sonnet |
|---|---|---|
| candidates | 5 settled, 5 completed, 0 invalid | 5 settled, 5 completed |
| baseline | 0.1172 | 0.1172 |
| draft, search | 0.9853 | 0.9864 |
| improves, search | 0.9871 / 0.9878 / 0.9877 | 0.9863 / 0.9862 / 0.9870 |
| final split, read once | **0.9888** (c0003) vs 0.985: supported | 0.9875 (c0004) vs 0.985: supported |
| session turns | 8 / 11 / 7 / 14 (median 11) | 12–17 |
| session wall clock | 53 / 41 / 22 / 64 s | 83–134 s |
| list-price cost | $0.00 | median $0.29 (subscription) |
| GPU-hours (training) | 0.06 | 0.13 |
| wall clock | 0.08 h | 0.14 h |

Both kill criteria cleared, at the same task and threshold as M1. The draft was a
two-conv CNN trained for five epochs, and the improves changed seed and epochs. Checked
for leakage: the candidate code reads only the training labels, no session hit the guard
(`Blocked` never appears in the four event streams), the served model in every
`config.json` is `local/gpt-oss-20b`, and the final split was read once by `lab run`.

**What went wrong, and is data.** Two of the four sessions (c0002, c0004) ended on a
provider error after their work was done:

```
400: request (40304 tokens) exceeds the available context size (32768 tokens)
```

Their candidates are `completed` because `code/run.sh`, predictions and `summary.md`
existed when the wrapper checked. Their `session.json` says `error_during_execution`,
which is the truth of the session. Pi's auto-compaction did not fire because the overflow
came in one step: a tool result of tens of thousands of characters, a training log or a
file dump, pushed the next request past the window. Fixed before the second probe: the
lab's Pi extension now clips every tool result to 16000 characters, head and tail, with a
marker (`LAB_TOOL_RESULT_MAX_CHARS`). Not fixed, and worth knowing: llama.cpp's cache
reads mean a session's cumulative input is cheap, but the context window is the hard wall
for a local model, and `worker_max_turns = 40` is far more turns than 32k tokens can hold
for a chatty model.

Other observations: the model wrote `summary.md` without being told twice, honoured the
seed from its job card, and never tried to background anything. Its prose overstates
("deterministic … the same weights will be produced"). That claim is the worker's and is
not measured, exactly the distinction the finding-card work exists for.

## Qwen3.8-27B Q4_K_M (`../labloop-pi-probe-qwen-20260915`, campaign `pi-probe-qwen38`)

| | Pi + Qwen3.8-27B Q4_K_M (local) | Pi + gpt-oss-20b | M1: Sonnet |
|---|---|---|---|
| candidates | 5 settled: 4 completed, 1 invalid (debugged) | 5 / 5 | 5 / 5 |
| draft, search | 0.9914 | 0.9853 | 0.9864 |
| later candidates, search | c0002 invalid; debug 0.9923; improve 0.9933 | 0.9871 / 0.9878 / 0.9877 | 0.9863 / 0.9862 / 0.9870 |
| final split, read once | **0.9937** (c0004) vs 0.985: supported | 0.9888 | 0.9875 |
| session turns | 11 / 13 / 14 / 16 | 8 / 11 / 7 / 14 | 12–17 |
| session wall clock | 324 / 762 / 310 / 795 s | 22–64 s | 83–134 s |
| output tokens per session | 7.6k / 17.4k / 7.0k / 17.9k | 1.5k–7.2k | — |
| GPU-hours (lease time) | 0.62 | 0.06 | 0.13 |
| wall clock | 0.63 h | 0.08 h | 0.14 h |

Same criteria cleared. The draft was a CNN with a held-out slice, 8 epochs. The last
candidate added ±2 px translation augmentation and stated its hypothesis before running,
unprompted, in the form the finding-card format asks for. Leakage checked as for gpt-oss:
training labels only, served model `local/qwen3.8-27b` in every `config.json`, the final
split read once.

**What went wrong, and is data.**

- **c0002 is invalid: the session ended at Pi's output token limit** (stop reason
  `length`, 13 turns, 762 s) while the model was still verifying its augmentation
  arithmetic by hand, and Pi ends a run on that stop. No `run.sh` was ever executed; the
  wrapper's contract check returned 2. The debug retry (c0003) ran the same code to
  completion in 14 turns. Two of the four sessions hit `length`; c0004 did so after its
  work was done, so it completed. Qwen3.8 spends output freely (17k tokens in the two
  long sessions against a `maxTokens` of 8192 per response): the per-response limit, not
  the context window, is its wall. Fixed after the probe, in the extension: a run that
  ends on `length` is sent a follow-up ("your last response was cut off; continue in
  short steps"), at most twice per session, and Pi resumes.
- **The guard fired five times in c0003**: the debug worker ran a `grep` for `LAB_…`
  variables whose pattern matched the label-path rule, was blocked each time, and moved
  on. A false positive that cost turns, not correctness; the rule stays.
- **No tool result was clipped** in this probe (the clipping landed before it started),
  and no session overflowed the context: Qwen's requests stayed well under 32k.

Speed: a dense 27B at Q4 on the 3090 is five to twelve times slower per session than
gpt-oss-20b at the same task, and the training lease shows it: 0.62 GPU-hours of lease
time for the same 0.06 of actual training, because the session sits inside the lease. On
MNIST that buys nothing measurable. On a task with headroom it may, and that is the next
campaign.

## What this does and does not show

- Shown: the Pi harness runs the loop end to end on a local open model with the same
  contract, guard, provenance and report as Claude Code, at zero usage-window cost;
  gpt-oss-20b clears M1's feasibility criteria on MNIST.
- Not shown: quality against Sonnet or any model (noise floor, one seed, five
  candidates); behaviour on a task with headroom (CIFAR-10, M2's task) or under the
  24-hour criterion; label separation (OFF here, by convention, as in M1).
- Next: the M2-style task on the better of the two local models, with
  `worker_max_turns` and the context window read together; then a hosted open model
  through the same `provider/model` id, which is the fork's path.
